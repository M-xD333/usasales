# O4: вес упаковки и измерение покрытия

Политика владельца: package/shipping приоритетен для расчёта доставки, net отдельно; неизвестный вес не мешает публикации. PARSER_VERSION=5 (раньше 4), RULES_VERSION=7 без изменения бизнес-порогов.

## Измерение до изменения

Снимок журнала: **8679 строк, 3913 последних source/listing/price предложений; у всех 3913 статус веса не измерялся**. Это не 0% найденного веса: прежняя схема вообще не записывала это поле. [Агрегаты по магазинам и категориям](evidence/weight-coverage-before-2026-11-27.json). Отсутствие записи/обрезка/падение не доказывают отсутствие веса.

Воспроизводимая read-only выборка: [30 предложений со статусами и происхождением](evidence/weight-sample-2026-11-27.json). 8 Amazon, 8 Best Buy, 8 Corsair и 6 товарных переходов из агрегаторов. Это группы маршрута получения, а не четыре независимых магазина; повторные товарные URL исключены. Старый net-парсер и новый pkg/net применены к одинаковым доступным HTML-ответам, не к разным удачным загрузкам.

| Маршрут | Офферов | Ответы | Старый найденный net | Новый pkg | Новый net |
|---|---:|---|---:|---:|---:|
| Amazon | 8 | 8 HTTP 200 | 0 | 0 | 0 |
| Best Buy | 8 | 8 HTTP 403 | 0 | 0 | 0 |
| Corsair | 8 | 8 ReadTimeout | 0 | 0 | 0 |
| Из агрегаторов | 6 | 6 HTTP 200 | 0 | 0 | 0 |
| Всего | 30 | 14 HTML / 16 недоступны | 0 | 0 | 0 |

Ноль — число **подтверждённых** весов среди 30 попыток, не доказательство отсутствия веса в магазине. В 14 HTTP200-ответах старый net-парсер тоже не нашёл значения; 16 карточек не были доступны для разбора. 11 успешных ответов имели только 3781 байт: HTTP200 не означает доступную карточку товара. При отдельной диагностической загрузке Amazon действительно вернул challenge, а Corsair отдал настоящую таблицу с `Weight: 2kg`: без уточнения вида веса новая политика оставляет её неизвестной. Это дополнительная диагностика, не подмена неудачных исходов выборки удачными. Обходов и повторяющегося перебора заголовков/адресов не было.

Небольшие реальные HTML-фрагменты сохранены в tests/fixtures/weight с происхождением. Они проверяют отрицательные случаи — ambiguous Corsair Weight и Amazon challenge. Положительные Shipping/Package/Item Weight и Package Dimensions проверяются синтетическими минимальными HTML в тестах: **успешное live-извлечение package на этой выборке не доказано**.

После внедрения новый ledger будет содержать optional weight_status `{found, source, kind, missing_reason}`. Старые строки остаются unmeasured. В этой фазе допускается только DRY_RUN: публикующий loop не развёртывается и реальные Telegram-посты не используются для проверки. Поэтому «после» по production-ledger пока не измерено; не следует выдавать fixtures за улучшение живого покрытия.

Команды (ничего не отправляют в Telegram):

```sh
DRY_RUN=1 python tools/weight_coverage.py --ledger data/offer_audit.json.gz --output /tmp/weight-coverage.json
# Набор 30 URL задаётся JSON {rows:[{url, category, source_id, title, route}, ...]}:
DRY_RUN=1 python tools/weight_coverage.py --sample-input /tmp/weight-input.json --sample-output /tmp/weight-sample.json
# Для честного сравнения парсеров необязателен явный --before-parser /path/to/old_product_weight.py.
```

## Данные и отправка

- `weight_pkg_kg` и `weight_net_kg` хранятся раздельно; для каждого обязательны source/field/ts в соответствующем provenance. Units обязательны: kg/g/lb/oz. Скаляр `weight_kg` остаётся net-экспортом совместимости, не подменяет новый package. Старый scalar без происхождения не выдается за package/net с выдуманным источником.
- Package: Shipping Weight, Package Weight, Weight (with packaging), в Amazon Package Dimensions только масса после `;`. Net: Product.weight (schema), Item/Product/Net Weight. Bare Weight, единицы длины, числа без единицы, диапазоны, compound mass и конфликтующие веса не используются.
- Многовариантная JSON-LD группа или неразрешённый selector цвета/размера/ёмкости остаётся unknown. Подход консервативен: даже точный дочерний URL в странице с несколькими Product не разрешает глобальную таблицу характеристик.
- Порядок подписи: `⚖️ Вес: 1 кг (с упаковкой)` → `⚖️ Вес: 0.5 кг (без упаковки)` → `⚖️ Вес: не указан`. Та же строка есть в коротком fallback и photo caption.
- Для combo/bundle не используется вес отдельного SKU как вес всего набора. Полный набор компонентов одного вида веса допускает `≈ … кг (сумма комплектующих)`, с количеством каждого компонента; это не измеренный вес посылки. Частичный/смешанный набор неизвестен. Явно измеренная упаковка самого bundle может иметь приоритет, если источник относится к bundle.
- O5: WEIGHT_ESTIMATES=0 по умолчанию. При явном включении есть небольшая таблица оценок для mouse/keyboard/headset/cpu/ram/ssd. Пометка «≈ … кг (оценка)» обязательна; не сохраняются как package/net и не считаются найденным измеренным весом. Значения ориентировочны, не тарифный вес перевозчика.
- Нормализованные веса из источника принимаются сразу. Фоновый lookup — максимум 2 процесса и 30 URL/проход, сигнал прерывания через 2 с; процесс изолирован, родитель никогда не ждёт сеть/будущий результат. В отправке используются только готовый ответ и кеш. Процесс, не закончивший lookup к отправке, не задерживает пост; остаётся unknown. DRY_RUN не запускает фоновые lookup и не пишет кеш.
- В обычном долгом цикле оценки готовые результаты пополняют кеш, даже если конкретный оффер ещё не отправляется. Если цикл закончен раньше lookup, незавершённые задачи прекращаются: полнота уступает запрету задерживать публикацию.
- Новые поля входят в pending/send payload до checkpoint статуса sending. validate/load/merge проверены; price floors, posted, receipt, delivery и publication_history не менялись. У уже сохранённых фактов доставки новые поля не дописываются.

## База знаний

`data/weight_knowledge.json.gz` — отдельный optional файл, максимум **500 000 байт gzip / 8 МБ распакованных / 10 000 ключей**, TTL180 дней. При переполнении удаляется старое. Ключи — ASIN, MPN+brand, UPC, либо точная нормализованная модель/название+brand; guard учитывает точное нормализованное название, ёмкость, цвет, размер, количество, bundle и condition. Полное название защищает и от неизвестных названий цветов (Obsidian/Porcelain), ценой дополнительных cache miss. Неполная модель сопоставления не повод заимствовать вес похожей модификации. Кеш намеренно консервативен: другое описание того же товара может дать cache miss.

Package/net с происхождением не смешиваются при merge. Файл сохраняется атомарно; sync/push и artifact recovery понимают оба файла, включая старые artifacts без knowledge. Ошибка/повреждение optional кеша не обнуляет его и не блокирует checkpoint/публикацию. Ограничен текущий файл, а не накопленная история бинарных Git-коммитов; частота/ветки состояния не менялись.

## API: только дизайн, всё OFF

Официальные поля проверены 2026-11-27; ключи не запрашивались, API-клиенты и подписки не добавлены.

| Источник | Проверенное поле | Вид и перевод | Что требуется |
|---|---|---|---|
| [Best Buy Products API](https://bestbuyapis.github.io/api-documentation/) | shippingWeight — shipping weight, pounds | package, ×0.45359237 | Developer key, согласование доступа/лимитов и точного SKU/варианта |
| Best Buy | weight — Product weight, string | net только если значение содержит явную единицу; не приписывать pounds строке без неё | Реальный ответ и unit-test fixture после получения ключа |
| [Keepa официальный Product.java](https://github.com/keepacom/api_backend/blob/master/src/main/java/com/keepa/api/backend/structs/Product.java) | packageWeight / itemWeight — integer grams, 0/-1 отсутствует | package/net соответственно, /1000 | Ключ и отдельное разрешение владельца на платный сервис/лимит затрат |
| [Amazon Creators ItemInfo](https://affiliate-program.amazon.com/creatorsapi/docs/en-us/api-reference/resources/item-info) | itemInfo.productInfo.itemDimensions.weight.displayValue + unit | net, перевод по unit; resource itemInfo.productInfo | Одобрение партнёрского доступа и credentials |

В проверенном Creators ItemInfo **не подтверждены** поля packageWeight/itemWeight: это названия Keepa, переносить их в Creators нельзя. Creators ItemDimensions не является упаковкой. Для package нужен отдельно документированный ресурс/ответ; до этого unknown. Не копировать unitCount как вес/количество частей комплекта наугад.

План после одобрения: асинхронный адаптер → проверка точного SKU/ASIN и variant guard → строгое преобразование единиц → раздельная provenance → existing knowledge → чтение готового веса без ожидания. Любая ошибка API, квота или ключ не влияет на разрешение публикации.

## Позднее редактирование Telegram: только дизайн, OFF

Сейчас last_delivery хранит только последнее message_id: этого недостаточно для безопасного массового редактирования. Понадобится отдельный ограниченный реестр отправленных сообщений с chat_id, message_id, kind text/photo, точным product/variant key, исходным текстом/caption hash, прежним weight provenance, sent_at и edited_at. Это новые поля с validate/load/merge и backup; publication_history floors не затрагиваются.

Предлагаемые лимиты для отдельного одобрения: окно 48 ч, до 2000 сообщений/1 МБ, максимум 10 правок за цикл/одна правка в секунду, только известный package вместо unknown/net и без изменения цены/магазина/условий. Проверять hash исходного текста, не затирать ручную правку; text → editMessageText, photo → editMessageCaption; учитывать лимиты 4096/1024 и 429 retry_after. Без достоверного message_id/исходного payload или при неоднозначном исходе не редактировать. На сбоe не перепубликовывать сообщение. Этот реестр, очередь edits и вызовы Telegram **не реализованы**.
