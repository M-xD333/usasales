# Отдельный журнал решений

`data/offer_audit.json.gz` — best-effort доказательства приёма и решения по предложению. Это отдельный файл: checkpoint, publication_history, posted, delivery, очередь и минимумы цен не изменены. В DRY_RUN журнал не создаётся. Сетевые ошибки источников по-прежнему отражаются в обычном логе: отсутствующий ответ не является увиденным предложением.

В каждой записи: `ts`/`last_ts` (Unix UTC, для отчётов переводить в Asia/Tashkent), source, store+store_basis, category, price, was+was_kind, title (160 символов), key, candidate_key, decision+reason, rules_version, seen_ts/published_ts. `key` — ASIN при явно переданном ASIN либо SHA256 canonical_url; если нет URL — ключ listing. `candidate_key` — SHA256 ровно одной известной товарной ссылки из store_candidates: это рекламируемая ссылка, не подтверждение перехода. Несколько разных кандидатов не угадываются. `store_basis=advertised` означает магазин по кандидату, `url` — по основной ссылке, `declared` — подпись источника. Цена/was не изобретаются: отсутствующие значения null, was_kind описывает тип заявленной базы.

Главные решения: not_evaluated (вход зарегистрирован, оценка не достигнута), evaluating/interrupted, rejected, queued/ожидание с конкретной причиной, duplicate, duplicate_in_batch, sending, delivery_unknown, published, queue_evicted. `published` записывается после успешного возврата Telegram send; это не подтверждение прочтения сообщения человеком. Reason редактируется штатным redact, заголовки и поля ограничены по длине.

Все нормализованные входы регистрируются **до** межленточной дедупликации. Повтор одной source/listing/цены в одном цикле объединяется; изменение цены фиксируется отдельно. Последнее решение в цикле заменяет предварительное. Неизменные решения объединяются в пределах суток UTC с интервалом ts…last_ts, переходы между решениями сохраняются. Отправки и неопределённая доставка не схлопываются с последующими повторами. Это журнал решений, а не дословная трасса каждой сетевой операции.

Перед обработкой входов сохраняется предварительный журнал, sending/published/delivery_unknown сохраняются немедленно; завершение process вызывает финальное сохранение. Atomic replace + fsync защищают существующий файл. При ошибке журнала публикационный процесс продолжается, в лог выводится AUDIT. Повреждённый файл не обнуляется. Авария между checkpoint и записью журнала может оставить неполную трассу: нельзя выводить решение из отсутствия строки.

Окно — последние **14 суток по last_ts**, максимум **1 500 000 байт сжатого файла**, дополнительно 25 000 строк / 24 МБ распакованных данных. При переполнении первыми удаляются старые записи; `started_at`, `truncated_before`, `dropped_capacity` показывают неполное покрытие. Гарантия размера имеет приоритет над полнотой 14 дней; поэтому при обрезке «не найдено в журнале» означает unknown. Состав записей специально ограничен, чтобы большая часть обычного потока помещалась, но объём реального потока ещё не измерен.

`workflow_git.py` переносит файл отдельно вместе с data/, сливает строки по id и версии решения, повторно применяет TTL/лимиты. Существующий failure artifact автоматически включает файл; восстановление понимает и artifact без журнала. Невалидный необязательный журнал не блокирует восстановление checkpoint. Тесты покрывают лимит на плохо сжимаемых строках, TTL, coalescence, сбой atomic replace, конфликт двух Git-писателей, artifact recovery, сбой журнала и mock-публикацию. Реальные Telegram сообщения для тестов не отправлялись.

Лимит относится к текущему файлу, не ко всей истории Git: gzip-файлы в частых state-коммитах могут увеличивать репозиторий. Частота коммитов и ветки состояния этим изменением не меняются. После накопления измерить фактический прирост; при необходимости отдельно согласовать хранение аудита в artifacts/другом хранилище с сохранением восстановления.

Для сравнения следующей недели: взять то же временное окно и канонические ключи ссылок; различать основной и advertised key, условия товара и цены. Сравнить с журналом решения и rules_version. При отсутствии merchant URL, предыдущей доставки, неполном source response или обрезке/аварии — unknown. Счётчик постов конкурента отдельно дедуплицировать по товару, цене и condition: повторы не требуют новых публикаций у нас.
